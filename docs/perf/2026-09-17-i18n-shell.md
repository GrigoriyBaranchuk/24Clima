# Словарь переводов в HTML: каждой странице только её неймспейсы (2026-09-17)

Продолжение PR #77. Принцип владельца: **каждая страница везёт только те
неймспейсы переводов, которые нужны её клиентским компонентам**; новая фича
заводит свой неймспейс и не расширяет оболочку.

## Что сделано

**Оболочка сужена до двух неймспейсов.** `CLIENT_SHELL_NAMESPACES =
["common", "whatsappMessages"]` — ровно то, что читают Header, BottomNav и
DesktopWhatsAppFab на любой странице. `tienda.cart` ушёл из оболочки в провайдер
магазина: TiendaCartLink рендерится в шапке только под `showCartLink`, а его
передаёт один лишь TiendaShell.

**Маркетинг вынесен в route-group `(marketing)`.** В обоих деревьях роутов
(`(es)` и `[locale]`) все маршруты, кроме `tienda/`, переехали в
`(marketing)/` — включая `page.tsx` главной. Скобочная группа на URL не влияет,
маршруты остались прежними (проверено диффом списка роутов из `next build`:
73 роута, идентичны). У группы свой layout с провайдером на
`[...CLIENT_SHELL_NAMESPACES, ...PUBLIC_SITE_CLIENT_NAMESPACES]`.

**Корневые layout-ы отдают только оболочку** — `pickMessages(messages,
CLIENT_SHELL_NAMESPACES)`.

**Провайдеры роутов:** `/tienda/**` → `[...SHELL, "tienda"]`;
`(marketing)/servicios/[service]` → `[...SHELL, ...PUBLIC_SITE, "services"]`
(страница чистки рендерит CleaningPackages и Calculator);
`(marketing)/consejos-y-guias/admin` → `[...SHELL, "tipsAdmin"]`.

### Почему именно группа, а не список в корневом layout

Первая попытка (корневые layout-ы получают `[...SHELL, ...PUBLIC_SITE]`) дала
всего 418–439 Б. Замер вскрыл два факта:

1. **React-Flight дедуплицирует payload.** Неймспейсы, попавшие и в корневой, и
   во вложенный провайдер, во втором лежат ссылками по ~30 Б, а не копиями. То
   есть вложенный провайдер магазина сам по себе почти ничего и не стоил.
2. **Пропсы КОРНЕВОГО провайдера сериализуются на ВСЕХ роутах**, включая
   `/tienda/**`: вложенный провайдер замещает словарь только для своих
   потомков, но родительский всё равно уезжает в HTML.

Значит единственный способ не везти маркетинговый словарь в магазин — убрать
его из общего предка. Отсюда группа `(marketing)`.

## Замер

Метод: из HTML склеиваются куски RSC-payload `self.__next_f.push([1,"…"])`,
разэкранируются, из них по балансу скобок вырезается каждый объект
`"messages":{…}`. Считается длина в байтах UTF-8 уже разэкранированного JSON —
одинаково для прода и для локальной сборки. Мобильный UA.

«Было» — прод https://24clima.com (main, PR #77). «Стало» — локальный
`next build` + `next start` этой ветки.

Маркетинговые страницы не выросли: они потеряли `tienda.cart`, а

```
провайдер 2 (магазин):  7207 Б — common=27 whatsappMessages=37 tienda=7102
```

Было (прод):

```
провайдер 1 (корневой): 7946 Б — common=955 whatsappMessages=375 calculator=687
  packages=914 contact=612 contactForm=648 whyUs=848 problems=1609 homeCta=308
  nosotrosCta=189 tips=224 tienda=429
провайдер 2 (магазин):  7186 Б — <маркетинг ссылками по ~30 Б> tienda=6714
```

### Почему 8,6 КБ, а не обещанные планом ~1,8 КБ

В плане ожидалось `common + whatsappMessages + tienda.cart`. Но провайдер
магазина отдаёт весь неймспейс `tienda` (7,1 КБ для es, 10,1 КБ для ru) —
корзина, аккаунт, чекаут, карточка товара, категории, — потому что он один на
все страницы магазина. Маркетинговых текстов там больше нет, и это был весь
смысл задачи; дальнейшее сужение — это уже дробление самого `tienda` по
подроутам (`tienda.cart` на /cart, `tienda.checkout` на /checkout и так далее).
Отдельная задача, в этот PR не входит.
